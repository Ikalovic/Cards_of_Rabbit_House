# Rabbit House 手作值班

桌面浏览器用的《请问您今天要来点兔子吗？》同人经营小游戏。主线把 Galgame 短剧情与轻量《老爹店》式多工位经营结合：在 12 分钟内接待顾客、读单、备料、组装、完成手工作业、检查、收入 StampBook、通过冲印机小游戏并亲手交付。

项目提供同源 Node.js 服务，负责匿名玩家会话、内存存档、校准出题、判题、卡片保存和冲印。React 前端与服务端一同部署，开发模式也使用同一套 API。

## 游戏模式

- **剧情经营**：教学关 5 位顾客、新手关 6 位顾客、剧情关 7 位顾客；每关营业时间均为 720 秒。三关依次引入顾客耐性、三张活动订单、有限材料、三次检查、双冲印机、补救操作和固定剧情。
- **生存天梯**：剧情关通关后开放。每天 720 秒，顾客数量、重叠程度、复杂卡概率与难题权重持续增长，没有永久数值升级，也不保证后期仍可全部完成。
- **自由工坊**：新档即可进入。自由拖拽、缩放、旋转、图层、受限画笔、StampBook 与独立冲印流程均不受剧情进度限制。

经营顾客均为原作角色。除了心爱、智乃、理世、千夜和纱路，新增麻耶、惠、青山、凛、摩卡、结良、冬优、夏明和映月，各有头像、订单、迎宾、催单、交付及离店文案。前三关排班为：

- 教学关：心爱、惠、夏明、千夜、映月。
- 新手关：麻耶、凛、千夜、冬优、青山、摩卡。
- 剧情关：心爱、青山、理世、千夜、结良、纱路、智乃。

生存班次每班抽取原五人中的两位，其余名额在九位新增角色间按种子均衡安排。新增角色美术使用项目提供的参考图，凛使用官网立绘；素材来源见 [`public/assets/ASSET_NOTES.md`](public/assets/ASSET_NOTES.md)。

生存奖励仅用于展示：第 1 日结算获得棉絮纸纹，单日平均品质达到 85 分获得玫瑰缎带，第 3 日结算获得花叶卡册，第 5 日结算获得智乃的小纸条。奖励自动应用于自由工坊和卡册，失败后仍保留，不改变材料、计时或评分；定义见 `src/content/survival-rewards.ts`。

剧情经营的一张订单依次经过六个工位：

1. 接单台：查看公开要求、偏好、禁忌与耐性；同时最多持有三单。
2. 备料台：选择卡纸、材质、形状、方向和固定槽位版式。
3. 组装台：把主体、字章、边框和装饰放到合法槽位，并选择尺寸、方向和层级。
4. 工艺台：按订单完成盖章、裁边、缎带、烫金或蜡封操作。
5. 检查台：消耗一次检查和 5 秒营业时间，统一列出当前版本的明显问题。
6. 冲印台：先明确收入 StampBook，再选机器、完成限时小游戏、等待冲印并手动交付。

每次冲印都要完成机器对应的小游戏。快印机使用找数、连线和快速辨认；精印机使用扫雷、数独、数学选择题与数学填空题。快印机更快，但复杂卡会固定损失机器品质分；精印机较慢，并完整保留精细效果。两台机器独立工作，机器运行、顾客耐性与营业时间不会因玩家切换工位或答题而暂停。

## 桌面操作

最低目标窗口为 `1280 × 720`，基准窗口为 `1440 × 900`；未针对移动端设计。

- 鼠标点击六个工位，或按数字键 `1`–`6` 切换接单、备料、组装、工艺、检查与冲印台。
- 按 `Q`、`W`、`E` 切换三张活动订单。
- 在组装台可点击素材后再点槽位，也可把素材拖到卡面槽位。
- 冲印校准开始后，退出或切走会按失败处理，并使该机器对本单锁定 30 秒。
- 全部顾客已交付或离店后，可主动“提前打烊”；游戏不会替玩家自动提前结算。
- 教学说明和剧情面板会暂停游戏控制的计时；普通工位操作、浏览器切页、刷新和关闭页面不会暂停。
- 标题、对白、营业、自由工坊、卡册和结算使用本地原作 BGM；工位切换不重启音乐。按钮、手作、保存、校准、出片与交付使用本地音效。首次点击或按键后启用声音，右下角“声音”可分别调节音乐 / 音效音量或全部静音，偏好自动保存。后台标签页暂停声音，返回时不补播旧提醒；恢复存档也不重播旧事件。
- 音频资源位于 `public/assets/audio/`，统一调用清单为 `src/content/audio.ts`；来源与署名见 [`public/assets/audio/SOURCES.md`](public/assets/audio/SOURCES.md)。BGM 优先 OGG、兼容回退 MP3；浏览器不请求外部音源。原始音乐、音效与未启用候选集中在仓库 [`materials/audio/`](../materials/audio/)，不进入 Docker 构建上下文。

## 正式数学题库

私有题库位于 `server/数学题库_分类整理版.json`，保持项目所有者提供的分类文件内容，仅打入服务器产物，不进入浏览器包。顶层必须且只能包含：

```text
单选题: Question[]
多选题: Question[]
填空题: Question[]
```

选择题需要正整数 `number`、非空 `stem`、恰好 `A`–`D` 四个选项和合法答案集合；填空题需要正整数 `number`、非空 `stem` 与至少一个明确答案。可选题图只能引用已登记的本地路径，可选表格必须具有等宽的非空表头和数据行。运行时不会从网络载入题图，也不会自行生成、推导或修补正式题答案。

当前原文件共 42 题，启用 41 题：23 道单选、9 道多选、9 道填空。单选第 23 题因题设自相矛盾且声明答案不属于 `A`–`D`，会被校验停用，不会猜测答案。客户端只收到题干、选项及单选/多选标记；答案集合留在服务器。多选须与正确集合完全一致；填空只做确定的字符与空白规范化，不执行表达式。

公式通过本地 KaTeX 渲染；题图随静态资源打包。所有题目的生成与判题均由本项目同源 API 完成，扫雷翻格也由服务器揭示安全格数字。浏览器不保存标准答案、雷区或数独解，也不执行判题。题目种子包含班次 ID；新班次重新出题，刷新同一班次恢复原题与截止时间。

## 存档与恢复

- 剧情进度、生存纪录、当前班次、作品、工坊草稿和冲印意图保存在服务器内存中；浏览器仅缓存当前会话的公开状态，所有保存通过带修订号的 API 原子提交。
- 每个匿名浏览器会话由 HttpOnly Cookie 隔离。不同浏览器配置文件拥有独立进度；同一配置文件的标签页属于同一玩家会话。当前未接入账号登录或跨设备同步。
- 容器/服务进程重启会清空全部会话、存档和私有题目。启动标识 bootId 改变后，已打开的页面会提示重新进入；刷新也从零开始。生产服务不挂载存档数据卷。旧版 localStorage / IndexedDB 游戏进度不会自动导入。
- 刷新会恢复同一班次、同一道题、原剩余期限、机器队列和锁定；不会借刷新重抽题目。
- 旧版六类自设顾客在读取时对应转换为麻耶、凛、冬优、摩卡、青山和结良，工坊草稿中的旧顾客标签也会更新。转换保留原订单要求、作品、材料、计时与修订号；读取不写盘，后续正常保存时才持久化角色信息。
- 离开页面后按真实经过时间推进。再次打开时若已超过闭店时间，会直接进入本班结算。
- 每次检查（包括教学示范）实际推进经营时钟 5 秒；`inspectionTimeOffsetMs` 随班次持久化，后续计时与刷新恢复继续计入该消耗，顾客、机器、校准及锁定同步推进。修改计时时须保持 `shiftTimeAt()` 的统一时间口径。
- “收入 StampBook”立即将不可变作品快照写入独立收藏，成功提交后即使班次未结算或被替换也保留；保存失败不应显示已收藏。查看作品、刷新或轮询均不会启动冲印。
- 结算后，离店顾客已开始但未归档的草稿进入卡册，可选择“带入自由工坊继续制作”。这是有损转换：可用贴纸、字章及相对位置等转入新工坊作品，卡胚、材质、部分素材和工艺效果可能改变或省略；界面会先列出差异，原草稿预览保留。转换见 `src/app/workshop-transfer.ts`，不携带经营订单、材料或冲印状态。
- 同一次冲印意图在重试和恢复时复用同一身份；保存成功但回执尚未落盘时会按相同意图恢复，避免重复冲印。
- 清除会话 Cookie 会进入新存档；已有服务器内存记录随服务重启清除。音乐音量等本机偏好可继续保存在浏览器，不参与玩家进度。

## 用 Docker 启动

在仓库根目录执行：

```bash
docker compose up --build -d game
```

打开 <http://localhost:8080>，健康检查地址为 <http://localhost:8080/healthz>。

更新源码后必须重新执行 `docker compose up --build -d game`，让页面、音乐、角色素材和服务端代码进入新镜像。`docker compose restart game` 只重启现有镜像，不会更新代码或素材。

镜像以非 root 用户运行 Node 24，同时提供静态页面和 `/api/`。`docker compose restart game` 即清空所有玩家进度；当前没有持久化存档；多实例部署需要另行实现共享会话。

停止服务：

```bash
docker compose down
```

改用其他宿主机端口：

```bash
GAME_PORT=8090 docker compose up --build -d game
```

开发容器：

```bash
docker compose --profile dev up game-dev
```

也可在 `game/` 目录直接运行：

```bash
npm ci
npm run dev
```

## 验证与生产构建

在 `game/` 目录执行（首次先运行 `npm ci`）：

```bash
npm run test:run
npm run typecheck
npm run build
```

也可从仓库根目录使用开发容器验证，无需宿主机安装 Node：

```bash
docker compose --profile dev run --rm game-dev sh -c 'npm ci && npm run test:run && npm run typecheck && npm run build'
```

日常修改只运行相关测试，例如 `npm run test:run -- server/service.test.ts src/test/puzzle-public.test.ts`。早期引擎/路线测试含本地私有题目夹具，迁移至远端判题契约后再用于完整回归；生产类型检查不编译测试夹具。

生产镜像只以 `game/` 为构建上下文。浏览器产物为 `dist/`，私有服务器产物为 `dist-server/`；只有前者由静态服务暴露。根目录的外部 API 示例请求、密钥和原始生成响应不会进入镜像，运行时不调用图像或文本生成服务。

## 卡册与冲印接口

领域契约位于 `src/domain/gateways.ts`，正常会话使用同源 Node.js API。接口须满足：

- `CardLibraryGateway.save()` 只保存不可变作品，不得创建冲印任务。
- `PrintShopGateway.startWorkshop()` 只服务自由工坊；`startShift()` 只在经营模式完成校准并持久化意图后调用。两条入口不能互相代替。
- `findByIntent()` 与 `get()` 必须是无副作用查询。查看卡片、加载缩略图、刷新、恢复和轮询不能启动冲印。
- 同一 `intentId` 必须幂等绑定同一 `snapshotId` 和同一上下文；出现冲突要拒绝，不能静默改绑。真正的“再印一份”需要新的显式意图。
- 经营模式回执必须原样保留 `receiptId`、任务身份、机器和班次身份，供本地状态机原子地把预留机位转成正式任务。
- 后端必须实施认证、CSRF 防护、输入校验、并发控制和错误映射；不能信任客户端分数、题目答案、机器状态或作品归属。
- 浏览器本地适配器与同源 HTTP 适配器遵循相同的保存、幂等和恢复约定。

经营操作及作品评分仍由客户端状态机推进，现有服务不等同于完整的服务端评分系统。
